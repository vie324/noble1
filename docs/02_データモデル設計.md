# ノーブル業務システム データモデル設計

作成日：2026-05-29
対象：Phase 0〜2（顧客・カルテ・回数券を中心とした中核モデル）+ 以降の拡張テーブル

---

## 1. 設計方針

1. **顧客を中心に据える** — 全モジュールは `customers` にぶら下がる。
2. **店舗横断 + 店舗別** — すべての主要レコードに `store_id` を持たせ、全店舗合算と店舗別フィルタの両方を成立させる。
3. **回数券は「台帳（ledger）」方式** — 残回数をカウンタで書き換えず、**消化を1件ずつ記録**し、残高は集計で導出する。返金・トラブル時に「誰が・いつ・どの施術で消化したか」を完全に追跡可能にする。
4. **カルテ＝来店記録（visit）に状態を持たせる** — `予定 / 未記入 / 記入済` の状態で「空のカルテの箱」運用と記入漏れ防止を実現。
5. **権限は Row Level Security（RLS）** — 役割（admin/manager/staff）と所属店舗でアクセスを制御。

### visits — 来店記録＝カルテ ★KaruteKun代替の核
| カラム | 型 | 説明 |

| id | uuid PK | |
| customer_id | uuid FK | 顧客 |

| カラム | 型 | 説明 |
|---|---|---|

| visit_id | uuid FK | |
| kind | enum | `before` / `after` |
| storage_path | text | Supabase Storage のパス |

### ticket_plans — 回数券マスタ
| カラム | 型 | 説明 |
|---|---|---|
| id | uuid PK | |
| name | text | 例：ハーブピーリング5回券 |
| total_count | int | 回数 |
| price | numeric | 販売価格 |
| valid_days | int | 有効日数（購入日から） |

### customer_tickets — 顧客の保有回数券
| カラム | 型 | 説明 |
|---|---|---|
| id | uuid PK | |
| customer_id | uuid FK | |
| ticket_plan_id | uuid FK | |
| purchased_at | date | 購入日 |
| expires_at | date | 有効期限 |
| total_count | int | 購入時点の総回数（マスタからコピー） |
| unit_price | numeric | 1回あたり単価（= price / total_count、返金計算用） |
| sold_by_staff_id | uuid FK | 販売スタッフ（販売実績分析用） |
| status | enum | `active` / `expired` / `refunded` |

> **残回数 = total_count − (ticket_usages の件数)**。カウンタを直接持たず**集計で導出**する。`v_ticket_balance` ビューで提供。

### ticket_usages — 回数券消化台帳 ★金額管理の心臓部
| カラム | 型 | 説明 |
|---|---|---|
| id | uuid PK | |
| customer_ticket_id | uuid FK | どの回数券を |
| visit_id | uuid FK | どの来店（施術）で |
| used_count | int | 消化回数（通常1） |
| used_at | timestamptz | 消化日時 |

> **不変台帳（append-only）**。修正は取消行（マイナス）で表現し、履歴を消さない。これによりダッシュボードの未消化残高と常に突き合わせ可能。

## 4. 主要ビュー（集計の単一窓口）

- **`v_ticket_balance`** … 顧客×回数券ごとに `残回数`・`未消化金額`（残回数 × unit_price）・`有効期限`・`期限切れ間近フラグ` を返す。ダッシュボードの「回数券未消化残高」はこのビューを使う。
- **`v_today_visits`** … 当日の `visits` を店舗・状態（特に `未記入`）で抽出。カルテ「今日」一覧用。
- **`v_body_part_monthly`** … `visit_items` を部位×月で集計（施術部位ごとの月次回数）。
- **`v_staff_repeat_rate`** … スタッフ別リピート率（管理者のみ閲覧）。

## 5. 権限（RLS）の考え方

| 役割 | 閲覧 | 編集 | 制限 |
|---|---|---|---|
| admin | 全店舗・全データ | 全データ | 分析の全指標を閲覧 |
| manager | 自店舗中心（必要に応じ全店） | 自店舗のカルテ・回数券 | スタッフ別指標は閲覧可 |
| staff | 自分の担当・所属店舗の来店記録 | カルテ入力 | **スタッフ別リピート率/回数券販売実績は閲覧不可** |

> クライアント要望「スタッフ本人には指標を開示しない」を RLS とビュー権限で担保。

## 7. 既存データ移行

現行スプレッドシート（`顧客管理` / `回数券マスター` / `スタッフ実績` / `日次売上` …）から：

- `顧客管理` → `customers` + `customer_tickets`
- `回数券マスター` → `ticket_plans`
- `スタッフ実績` → `staff`（実績数値は移行後はカルテから自動算出に切替）
- `日次売上 / メニュー別売上` → 過去分は分析用に取込、以降はカルテ起点で自動生成

> 移行は一度きりのスクリプト（CSVエクスポート → 変換 → `insert`）で実施。

詳細な物理スキーマは `noble-app/supabase/migrations/0001_init.sql` を参照。
